# Babysit the change or PR

MUST keep working until the user-requested delivery stage is verified. Establish that stage from the request and existing session authorization: local changes, a draft or ready PR, merge, or deployment. MUST NOT infer permission to push, merge, or deploy solely from this skill being installed or applied globally. A request to babysit through merge and deployment authorizes those stages. Honor explicit boundaries such as “do not deploy” or “do not restart.”

Before acting, identify the repository's branch rules, review mechanism, required checks, publication workflow, and deployment target, as relevant to the authorized stage. Read the actual CI and deployment configuration. MUST distinguish completed actions from proposed actions and local verification from production evidence.

1. Finish the change and relevant tests. Review the diff and preserve unrelated work. If PR delivery is authorized, create a focused branch and commit, push it, and open a PR describing the behavior, verification, and material limits. Prefer the connected GitHub tools for PR operations when available. If the requested outcome is a local change or a draft PR, verify that outcome and finish there.
2. For a PR proceeding through review, request Codex Code Review using the repository's configured mechanism when available. The direct trigger is a PR conversation comment containing `@codex review`. Requesting this review is part of the authorized PR workflow. Verify acceptance and wait for the result; an empty comment list immediately after the request is not a completed review. Codex can complete a review in an updated PR summary comment and receipt without creating a GitHub Review object. Check the reviewed commit and findings there as well as review threads. If Codex review is unavailable, report that gate explicitly and follow the repository's actual review requirements; MUST NOT claim a review occurred.
3. Check the review discussion, unresolved threads, and CI for the current head commit. Address actionable feedback and failures, rerun relevant checks, push the revision, and request another review when the new diff warrants it. Explain any finding intentionally left unchanged in the PR. Keep polling while review or checks are pending, with concise progress updates. A ready-PR request finishes once review and required checks are complete.
4. When merge is authorized, review is complete, and required checks pass, merge using the repository's allowed method and an expected head SHA. If merge authorization is missing and merge is needed for the requested outcome, present the ready PR and ask for it. MUST NOT merge over unresolved substantive findings or failing required checks without a user decision. A merge-only request finishes after verifying the merge commit and reporting any automatic workflows it triggered.
5. When deployment is authorized, follow the post-merge workflow until the artifact for the merged commit is published. For container workloads, record its tag and digest. Watch the configured automatic deployment and verify that the live workload runs the intended artifact, has completed its rollout, and passes a relevant health or user-facing check. For Kubernetes and Flux, inspect the configured context, ImagePolicy digest, ImageUpdateAutomation, deployment image, pod readiness and restarts, and pod `imageID`. MUST NOT assume a `latest` tag, green CI check, or ready old pod proves delivery. MUST NOT manually restart or change deployment configuration just to force a rollout unless that work is authorized and necessary.

If an external service stalls or fails, inspect the concrete gate and continue with fixes within scope. MUST NOT repeatedly retry mutations without checking their state. Report a persistent external blocker with the PR, commit, workflow, and deployment state needed to resume.

Finish with evidence appropriate to the requested stage: local validation, PR link and review outcome, merge commit, published artifact identity, and observed deployment health, or the exact unfinished gate. Omit stages that do not apply.
